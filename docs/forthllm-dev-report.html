2. Fork question

Question: "Since we don't own llama.cpp, should we fork it and just merge llama.vm into it?"

Recommendation: fork llama.cpp — yes; merge the llama.vm pager into it — no.

Thinking ForthLLM is a llama.cpp feature (flags in common/, engine + KV surgery in the core, hooks in tools/server). Its durable home is a feature branch of llama.cpp, not a patch file that lives in another repo. A local feature branch is the minimal fork; a GitHub fork is only needed if we want to push/share, and gh is not authenticated in this environment, so the local branch is the fork for now — rebase-ability onto upstream is preserved either way.

The pager, by contrast, is deliberately independent: it has its own build, is loaded at runtime via dlopen as libggml-llamavm-{cpu,gpu}.so into any llama.cpp build, and has a standalone test suite (test_pager, test_gguf, llama-vm bench|tiered). Merging it into llama.cpp would entangle two build systems and destroy the standalone use-case that is a core part of the project's objective. The integration point is already clean (tensor_buft_overrides + the dlopen shim). So: keep two repos, and let llama.vm/patches/ record the llama.cpp-side work.

3. Phase 4a — replace the placeholder scaffold

What was done: replaced llama.vm's token-level placeholder (forthllm::context_manager::process_chunk(tokens), which filled "summaries" with sin(i + chunk_id) * 0.1f and never touched a model) with a faithful port of the tested llama.cpp engine into namespace forthllm:

  • summarize() — real KV-row pooling (attention / mean / last) into S summary rows.
  • stack — chunk stack with lru / lfu / fixed-window eviction.
  • squeezer — JL projection → per-vector min/max 8-bit quantization → BWT (the old [-1,1] quantization assumption is gone; values outside [-1,1] now survive).
  • bwt_transform — uint8_t comparator + exact LF-mapping invert (the bytes≥128 case is now tested; the old invert was broken).
  • jl_projector — deterministic Gaussian N(0, 1/output_dim) from a seed.

The token-level context_manager/chunk_summary API was removed (it had no real semantics); the KV-row API (summarize + stack) replaces it. fm_index was kept as a standalone utility. test_forthllm (8 tests) and test_squeezer (6 tests) were rewritten to test real behavior.

Thinking Two implementation options were on the table: (a) a thin re-export that calls llama.cpp's C API, or (b) porting the self-contained math into llama.vm. Option (a) was rejected because the real engine's API is KV-row-level and its C API needs a llama_context* — a re-export would make llama.vm's ForthLLM depend on a live llama.cpp context and break the repo's standalone value. Option (b) works because the engine's model-agnostic math depends only on llama.h (for llama_pos) and std headers — no ggml — so it ports cleanly and keeps llama.vm self-contained and unit-testable.

The token-level context_manager could not be made "real" without a model (you cannot summarize raw token ids into an embedding without weights), so keeping it would have meant keeping a lie. Removing it and exposing the KV-row API is the honest port. One interaction bug was caught by the tests: the new BWT appends a 4-byte row index for invertibility, which corrupted fm_index (it consumed the BWT as its index) — a SIGSEGV and a wrong count. Fix: fm_index strips the 4-byte suffix. A residual, pre-existing quirk remains: fm_index::locate positions are off for a circular BWT without a sentinel; count is correct, and the test asserts count + position count, not exact positions.

Result: full ctest suite green (11/11). Committed as 1bbbb36.

4. DeepSeek-V4 finding (re-scopes 4c)

The user's actual model (DeepSeek-V4-Flash, the test-forth-deepseek() target) uses llama_kv_cache_dsv4. Investigating it for 4c revealed it is not a standard MLA cache:

  • kv_raw — a llama_kv_cache_iswa (normal raw/SWA token cache; the sliding-window half is what DSV4 raw attention reads).
  • kv_csa / kv_hca / kv_lid — three compressed K-only block caches (storage only; visibility and block planning live in llama_kv_cache_dsv4_context / llm_graph_input_dsv4).
  • csa_state / hca_state / lid_state — ring compressor states (row id = pos % ratio); the compressed rows are graph outputs (per-ubatch comp_plan recipes), not stored rows.
Thinking Two facts make 4c a design problem rather than a port. First, the C API rejects DSV4 because llama_forthllm_compact does dynamic_cast<llama_kv_cache*>(memory) and llama_kv_cache_dsv4 derives from llama_memory_i, not llama_kv_cache — so the cast fails and it logs "not supported". Second, llama_kv_cache_dsv4::get_can_shift() is hard-disabled ("compressed row metadata uses block-derived positions"), so the K-shift re-rotation machinery the Qwen3.5 path relies on is unavailable. Conceptually, DSV4 already compresses its KV (the block caches are the compression); ForthLLM on top would be compression-on-compression, and the ring states are graph-computed, not rows we can summarize in place. Realistic targets, in decreasing confidence: (i) compact the kv_raw SWA cache (bounded window — small win), (ii) operate on the compressed block caches (requires re-deriving ring states — graph work), (iii) a DSV4-specific compaction that respects the comp_plan/ratio structure. Conclusion: 4c needs its own design pass before implementation; do not attempt it as "just make the cast succeed".

5. Phase 4b — wire max_stack_depth + eviction

What was done: the --forthllm-max-stack-depth and --forthllm-eviction flags now take effect.

  • llama_forthllm_params gains max_stack_depth + eviction, carried from common_params_forthllm through common_forthllm_compact. max_stack_depth <= 0 keeps the previous no-limit behavior.
  • llama_kv_cache::forthllm_compact computes n_keep = min(n_chunks, max_stack_depth) and n_drop = n_chunks - n_keep. In the oldest→newest chunk loop, the oldest n_drop chunks are dropped entirely (all C cells freed, subsequent cells shifted left by C, no summary rows); the most recent n_keep chunks are summarized as before (C−S freed).
  • A dropped chunk is reported as {pos0, n_tokens=C, n_freed=C} (so n_summary = 0); the server token-sync now counts filled entries (not n_freed/(C−S)) and erases [pos0 + (n_tokens − n_freed), pos0 + n_tokens) per chunk — the whole chunk when dropped, [pos0+S, pos0+C) when summarized.
Thinking The original plan was to drive eviction from a per-slot llama_forthllm_stack in the server hook. That was rejected on inspection: the compaction re-derives the layout from the cells on every call (it has no persistent notion of which cells are summaries), so a persistent stack in the server would not match what the cache actually does. Integrating the eviction into the compaction — dropping the oldest chunks during the same oldest→newest pass that summarizes the rest — is simpler and correct, and reuses the exact validated primitives (seq_rm, pos_add, head tracking) with only the freed/shifted count changed (C instead of C−S). Cell indices are stable across the shifts (only positions move, and they all move together, so contiguity is preserved), which is what makes the drop branch safe.

Two consequences had to be handled downstream. The chunk count can no longer be derived as n_freed/(C−S) (dropped chunks free C, not C−S), so the server counts filled chunk_info entries instead. And the per-chunk erase range must use keep = n_tokens − n_freed (which is S for summarized chunks and 0 for dropped ones) rather than a global S.

The squeezer/jl_dim were deliberately not plumbed into the C API: they describe the stored/offloaded representation (in-cache summary rows stay head-dim), so their consumer is state save/load, which does not exist yet. Adding unused fields to a public C struct would be sloppy; they remain carried in common_params_forthllm and are documented as future. All three eviction policies currently reduce to "drop the oldest" — importance-based (lfu) eviction needs per-chunk attention counts, which is a callback into the attention path and is deferred.

Result: E2E-validated (below). Committed as 342c7c4f3.

8. Remaining work — Phase 4c (MLA / DeepSeek-V4)

4c is the user's actual model and the highest-value item, but it is the largest and needs a design pass first. Three questions to settle before implementation:

  1. Which cache to compact? The raw SWA cache (bounded window — small win) vs. the compressed block caches (already compressed — ForthLLM would be a second compression).
  2. How do ring states re-derive after compaction? The csa/hca/lid states are graph-computed ring states (pos % ratio); dropping/summarizing rows must keep them consistent, which is graph work, not row surgery.
  3. Is K-shift re-rotation available at all? get_can_shift() is currently hard-disabled for DSV4; the Qwen3.5 path's re-rotation of shifted keys has no DSV4 equivalent yet.
